The notebook itself is **not** copied here. It is an interactive teaching artefact whose value

## ⚠ The notebook has a dependency that does not ship

Cells 19, 32, 33, 36 read:

```python
context.textFile("hdfs://namenode:9000/data/films")
```

**`/data/films` is not in the predecessor repository.** Its `.gitignore` contains exactly one
entry — `data` — so the dataset was always local to whoever wrote the notebook. Anyone cloning
that repo hits the same wall.

This matters beyond the move: an earlier draft of feature 003 required parity output to be
"byte-identical to the same job on `docker-hive`", which was never achievable by anyone without
that file. **Feature 003 therefore defines its own deterministic input** (below) rather than
depending on a dataset nobody has. Determinism comes from generating the input, not from
inheriting it.

## What the notebook actually exercises

Four groups, in order:

### 1. RDD from a local file (cells 6–17)
`textFile` on a local path → `map(split(" "))` → `flatMap` → `map(w -> (w,1))` →
`reduceByKey(add)` → `collect`. Classic word count over a small local file.

### 2. RDD from HDFS (cells 19–20)
`textFile("hdfs://namenode:9000/data/films")` → `take(10)`. **This is the integration that
matters** — Spark reading HDFS through the NameNode. Everything else is Spark-local.

### 3. RDD from a Python object (cells 22–30)
`parallelize` → `map` → `flatMap` → `count` / `take` / `collect`. Exercises the executor path
without touching storage.

### 4. Word count over HDFS, two ways (cells 31–36)
- **High performance:** `map(split(","))` → `flatMap` → `map(w -> (w,1))` → `reduceByKey`
- **Low performance:** the same via `groupByKey`

The pedagogical point is the shuffle difference between `reduceByKey` and `groupByKey`. Worth
preserving as a fixture because it is a genuine YARN/shuffle exercise, not just a smoke test.

### Session setup (cell 1)
`SparkSession` built with `enableHiveSupport()` — so the notebook expects a working Hive
metastore even where it does not query Hive directly.

## The replacement fixture feature 003 should build

`tests/fixtures/mapreduce_wordcount.py` — headless, self-contained, deterministic.

**Input:** generated by the fixture, not supplied. A CSV written to
`hdfs:///parity/input/films.csv`, with a fixed row set committed alongside the fixture so the
expected output is computable by hand and stable across runs. Comma-separated, to match the
notebook's `split(",")`.

**Operations, mirroring the notebook:**
1. `textFile` the generated HDFS path — proves Spark↔HDFS.
2. `map(split(","))` → `flatMap` → `map(w -> (w,1))` → `reduceByKey` → `sortByKey`.
3. Assert the result equals the committed expected output exactly.
4. Repeat via `groupByKey` and assert both agree — preserving the notebook's lesson while
   turning it into a real assertion.
5. Build the session with `enableHiveSupport()`, as the notebook does.

**Sort before comparing.** `reduceByKey` output ordering is not guaranteed; an unsorted
comparison is a flaky test waiting to happen.

**Expected output** is committed as a fixture file. Because the input is generated and the
transformation is pure, it is fully determined — no reference cluster needed.

## Keeping the notebook as a teaching artefact

Feature 003 needs the *workload*. The *notebook* is still worth carrying, on the optional
`edge` host, as the thing a learner opens. Two rules if it is ported:

- Point it at the generated `/parity/input/films.csv`, not `/data/films`, so it works on a
